# Effective-Dating Review

## Common convention

All business validity uses `effectiveFrom DATE` inclusive and nullable `effectiveTo DATE` exclusive: `[from,to)`. `NULL effectiveTo` is open-ended. Adjacent rows where prior `effectiveTo = next effectiveFrom` do not overlap. System audit instants use `timestamptz` and never substitute for business dates.

| Structure                        | Overlap policy                                                                                                                            | Correction and historical query                                                                                                        |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| ServiceEngagement                | Same resolved property/space scope cannot have incompatible ACTIVE-effective models at one date; compatible explicit override is recorded | End-date and add successor; signed/posted history retains engagement ID/version; query by `from <= asOf AND (to IS NULL OR asOf < to)` |
| PropertyOwnership                | Same owner/property duplicate ranges excluded; configured active ownership total must equal 100% after verification                       | Retroactive correction requires approval and cannot rewrite issued/payout history                                                      |
| PropertyOwnerEntitlement         | No duplicate overlapping entitlement for same ownership; active payout percentages validated to 100% where payout enabled                 | Successor row; statements cite calculation snapshot/effective facts                                                                    |
| PropertyBranchAssignment         | Exactly one operating branch per Property at an effective date                                                                            | Transfer closes prior row and opens successor atomically; historical reports use assignment at business date                           |
| RentableSpaceVersion             | Exactly one active version per space/date                                                                                                 | Measurement correction creates successor; LeaseVersion retains prior version ID                                                        |
| RentableSpaceParentHistory       | One parent per child/date, same property, no cycle; relation covered by active versions                                                   | Split/merge creates new relations/successors; prior topology remains queryable                                                         |
| EmployeeBranchAssignment/role    | Duplicate identical scope ranges excluded; multiple distinct branches allowed for MULTI_BRANCH                                            | End-date/reassign; authorization evaluates current date and audit preserves prior scope                                                |
| Recurring schedules              | Same lease/charge purpose cannot have conflicting active schedules                                                                        | Successor schedule; generated Charge stores schedule ID/calculation inputs                                                             |
| Approval/legal/template versions | One applicable approved version for defined scope/date/priority                                                                           | Never edit a version already used; add successor and retain reference from action/document                                             |

Future-dated changes are allowed if they do not violate scheduled reservations, possessions, engagement compatibility, or approved policy. Database exclusions/triggers and application locks enforce concurrent updates.
